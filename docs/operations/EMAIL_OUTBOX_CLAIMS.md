# Email delivery claims and recovery

Update, 26 October: the immediate `EmailService.send(... dispatchImmediately)` path now uses the same claim, fenced status/attempt transaction, deadline and retry-delay helpers as the scheduled dispatcher. It reads persisted content and the actual attempt count. Five additional real PostgreSQL cases cover public immediate send, 32 mixed immediate/scheduled workers, stale immediate success/failure against a scheduled replacement and current fourth-attempt content. Combined PostgreSQL/Redis65cases pass with cleanup;18focused email tests, backend types and lint pass. No real emails were sent by these fixtures.

Each delivery attempt claims the current row using a fresh random owner token, database UTC time and `FOR UPDATE SKIP LOCKED`. A stale due-page snapshot cannot steal an active claim or bypass a changed availability date. The provider receives the current payload and the established stable idempotency key; the logged attempt number comes from the atomic increment, not the earlier scan.

Completion, suppression and failure update only the claim owner and write their delivery attempt in the same database transaction. A late worker cannot overwrite a replacement worker or insert a stale delivery receipt. Expired workers on the eighth attempt become explicit exhausted failures. The existing immediate retry for password-reset timeout failures remains intact, with the existing capped backoff for other failures. Provider waits have a 30-second deadline and clean up their timers; leases last 60 seconds.

Verification: seven email unit tests, backend types and source/helper lint passed. The real PostgreSQL/Redis checkout fixture passed 46 cases, including seven new email cases: 32 competing sends, late success, late failure, changed availability/current payload, final-attempt recovery/password-reset retry, actual receipt-constraint rollback and a locked-row skip. The separate file-deletion/delivery regression passed 14 cases, including 26 fresh email suppression guards with no transport calls. These email tests use synthetic transport responses, not real email delivery.

[Resend idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys) are retained for 24 hours. A request timeout cannot cancel an already accepted external send; the stable key protects retries within that provider window. This is not an unlimited exactly-once guarantee. No schema migration is needed for this tranche. Drain old dispatcher workers before rollout because they lack ownership fencing.
