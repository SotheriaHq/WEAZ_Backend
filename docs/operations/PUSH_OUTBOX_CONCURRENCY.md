# Push queue and receipt concurrency

Each attempt claims the current outbox row with a unique UUID owner, database time and `SKIP LOCKED`. Eligibility, payload and attempt count come from the current row. Completion, failures, accepted tickets and token changes are guarded by that owner. Crashed final attempts become explicit exhausted failures. Provider calls have a 30-second deadline; leases renew before each device chunk.

Accepted tickets commit after each chunk. A later chunk failure preserves them, and a retry selects only active tokens without an accepted pending/OK ticket. Transient ticket failures and missing tickets are retryable. An accepted Expo ticket means the service accepted the request; actual delivery is resolved separately from its receipt.

Every token registration rotates a UUID version. New receipts snapshot that version. Both immediate ticket handling and later receipt polling can change only the matching token registration and recipient. This also covers registrations occurring at the exact same millisecond. Receipt resolution is conditional on PENDING, so duplicate/conflicting pollers cannot overwrite a resolved result or count a token failure twice. Receipt resolution and token deactivation are one SQL command. Outbox completion checks current SENT state and unresolved receipts. Expired lookups retain an explicit `ReceiptExpired` error rather than an indefinite pending state.

Migration `20261026093000_push_receipt_registration` adds the token version and receipt snapshot. Existing receipts have no proven version and are not backfilled by guessing. Their delivery outcomes remain recorded; current token registrations are protected. The separate compatibility-retirement gate must inspect any remaining unversioned records before tightening the nullable historical snapshot contract. Drain old API/dispatcher workers before applying migrations and starting the new version. The migration has been applied only in disposable verification databases so far.

Verification on 26 October: 60 combined PostgreSQL/Redis cases pass with cleanup, including 14 push claim/receipt cases; 29 focused unit tests across four suites, backend types and source/helper lint pass. A separate 14-case query/deletion regression preserves three badge aggregates and 26 current token guards for 26 pushes with no transport calls. Final push transports in these fixtures are synthetic; the Redis recovery case uses an actual isolated BullMQ queue and processor.

[Expo's delivery guidance](https://docs.expo.dev/push-notifications/sending-notifications/) distinguishes accepted tickets from delivery receipts. Network acceptance followed by a lost response or database outage can remain ambiguous; these changes do not promise exactly-once device delivery or verify native permissions. Device UX remains a separate release gate.
